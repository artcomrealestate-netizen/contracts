# نظام إدارة عروض الأسعار والعقود والفواتير
## Software Requirements & System Architecture Specification

**Version:** 1.0  
**Target:** Mobile Application  
**Frontend:** Flutter  
**Backend:** Firebase / Serverless Architecture  
**Authentication:** Firebase Authentication  
**Database:** Cloud Firestore  
**File Storage:** Firebase Cloud Storage  
**Notifications:** Firebase Cloud Messaging  
**Backend Logic:** Cloud Functions / Trusted Server-side Services  
**CI/CD:** GitHub Actions أو Bitbucket Pipelines  
**Version Control:** Git  
**Environments:** Development / Staging / Production

---

# 1. الهدف من النظام

النظام عبارة عن منصة داخلية لإدارة دورة حياة المستندات التجارية والعقود، تبدأ من بيانات العميل والعقار والفاتورة المرجعية، مروراً بإنشاء العقد ومراجعته واعتماده، وصولاً إلى إنشاء النسخة النهائية وتجميدها وأرشفتها.

النظام لا يعيد بناء تطبيق الفواتير الحالي، وإنما يتكامل معه.

الدورة الأساسية:

```text
Customer
   ↓
Property
   ↓
Quotation / Existing Invoice
   ↓
Create Contract
   ↓
Draft
   ↓
Submit for Approval
   ↓
Admin Review
   ├── Reject → Employee Revision → Resubmit
   │
   └── Approve
          ↓
       Finalize
          ↓
      Generate PDF
          ↓
       Immutable
          ↓
        Archive
```

# 5. RBAC Architecture

لا يعتمد النظام على إخفاء الأزرار في Flutter فقط.

يجب تطبيق الصلاحيات على مستويين:

```text
Flutter UI Authorization
+
Backend / Firestore Security Authorization
```

مثلاً:

```text
Employee:
contract.create = true
contract.edit = true
contract.submit = true
contract.approve = false

Admin:
contract.create = true
contract.edit = true
contract.submit = true
contract.approve = true
contract.reject = true
```

الواجهة تخفي الوظائف غير المسموحة.

لكن Security Rules / Backend تمنع الوصول حتى لو حاول المستخدم إرسال Request يدوياً.

# 11. Financial Snapshot

**لا يتم تحديث الـ Snapshot تلقائياً.**

# 15. Locked Clauses

بعض البنود لا يجوز للموظف تعديلها.

مثلاً:

```text
isLocked = true
```

إذا كان:

```text
isLocked = true
```

فالموظف:

- لا يعدل
- لا يحذف

بينما Admin يستطيع تعديل Template الأصلي وفق الصلاحيات.

# 16. Contract Lifecycle

الحالات الرسمية:

```text
DRAFT
PENDING_APPROVAL
REJECTED
APPROVED
FINALIZED
ARCHIVED
CANCELLED
```

المسارات المسموحة:

```text
DRAFT
  ↓
PENDING_APPROVAL
```

```text
PENDING_APPROVAL
  ↓
APPROVED
```

أو:

```text
PENDING_APPROVAL
  ↓
REJECTED
  ↓
DRAFT
  ↓
PENDING_APPROVAL
```

ثم:

```text
APPROVED
  ↓
FINALIZED
  ↓
ARCHIVED
```

# 17. State Machine Rules

لا يسمح للعميل بتحديد status بشكل حر.

مثلاً يجب منع:

```text
Employee:
DRAFT → APPROVED
```

ومن:

```text
REJECTED → FINALIZED
```

ومن:

```text
DRAFT → ARCHIVED
```

كل transition يجب أن يكون معرفاً مسبقاً.

مثلاً:

```text
submitContract()
approveContract()
rejectContract()
finalizeContract()
archiveContract()
```

---

# 18. Approval Process

عند Submit:

```text
DRAFT
→ PENDING_APPROVAL
```

يتم:

1. Validation
2. التأكد من اكتمال البيانات
3. التأكد من وجود Invoice إذا كان إلزامياً
4. التأكد من وجود البنود المطلوبة
5. تسجيل Audit Log
6. تحديث الحالة
7. إرسال Notification للـ Admin

# 35. Firestore Transactions

تستخدم Transactions / Atomic Operations للعمليات التي تتطلب consistency.

خصوصاً:

- Serial Numbers
- Contract Finalization
- Critical State Transitions
- Snapshot Creation
- Audit Logging

مثلاً Finalization:

```text
Validate State
      ↓
Validate Permission
      ↓
Create Snapshot
      ↓
Change Status
      ↓
Create Audit Record
      ↓
Commit
```

يجب ألا تحدث بعض هذه الخطوات بشكل منفصل بحيث ينجح بعضها ويفشل البعض الآخر.

# 80. Architecture Principle النهائي

المنتج ليس:

```text
Mobile App + Firebase
```

بل:

```text
                    ┌──────────────────────┐
                    │    Flutter Mobile    │
                    └──────────┬───────────┘
                               │
                    Authentication / API
                               │
                    ┌──────────▼───────────┐
                    │   Business Layer     │
                    │ Workflow / RBAC      │
                    │ Validation / Audit   │
                    └──────────┬───────────┘
                               │
              ┌────────────────┼────────────────┐
              │                │                │
        ┌─────▼─────┐    ┌─────▼─────┐   ┌─────▼──────┐
        │ Firestore │    │  Storage  │   │ Functions  │
        └───────────┘    └───────────┘   └─────┬──────┘
                                               │
                                      ┌────────▼────────┐
                                      │ Invoice System   │
                                      │ Existing App     │
                                      └─────────────────┘
```

والهدف النهائي هو أن يكون كل مستند قابلاً للتتبع من:

**Customer → Property → Invoice → Contract → Approval → Version → Final PDF → Archive**

مع معرفة:

**من أنشأه؟ من عدله؟ من رفضه؟ لماذا؟ من اعتمده؟ متى؟ وما هي النسخة التي تم اعتمادها فعلياً؟**

وهذا هو المستوى الذي يجعل النظام **Production-grade** وليس مجرد CRUD application.
